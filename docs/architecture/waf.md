# WAF

## 要件・前提
- SQLインジェクション、XSSを防ぐ。アプリケーションコードにはNextJS/Djangoを導入しているので、これらはデフォルトでSQLi対策などが行われてはいるが、そもそもインフラ構成の内部に不正なリクエストを受け付けないようにする。そのため、CloudFrontの入り口にWeb ACLを付与する。
- アカウント乗っ取り攻撃による不正アクセスを防止する。認証が必須なリクエストだが未認証だった場合、Connito hosted UIにリダイレクトし、これはCloudFrontを経由しないので、Cognito ユーザープールにもWebACLを付与する必要がある
- DDos攻撃も軽減する。Cognito Hosted UIのURLを直叩きされることによるDDos攻撃も考慮する

### 選定理由
- インフラ構成(アプリケーションコード除く)全体がAWSサービスで構築しているので、AWSサービスとシームレスに連携できるAWS WAFを選定
- アプリケーション全体の入り口はCloudFrontなので、ここでWeb ACLを付与することで、不正なリクエストをそもそもアプリケーションに持ち込ませないようにする。ただ、動的ページにて、認証必須リクエストで未認証の場合、Cognito Hosted UIにリダイレクトされる。このURLを直叩きされる場合は、CloudFrontを経由しないので、この経路も考慮する必要がある
- Web ACLは下記3箇所に付与する
  - CloudFront(us-east-1)：SQLインジェクション、XSS、DDos対策のマネージドルールを付与。CloudFrontに付与する場合は、WAFをus-east-1に作成しなければいけない制約に注意
  - Cognito B側ユーザープール(ap-northeast-1)：DDos対策を付与。B側はMFAログインを必須にしており、アカウント乗っ取りリスクが低いと判断し、DDosのみとする
  - Cognito C側ユーザープール(ap-northeast-1)：DDos、アカウント乗っ取り対策を付与。C側はMFAを有効にしていないので、ATPルールを付与
- Cognito用Web ACLのステートは、WAF用のステートに配置する。Cognitoに付与するとはいえ、Webアプリケーションへの攻撃を軽減する、という役割から、WAFと同じであると判断したため。

### 通信経路
- ブラウザ → CloudFront(Web ACLをつけているのでここでリクエスト検査)
- ブラウザ → Cognito Hosted UIページ(Web ACLをつけているのでここでリクエスト検査)

### セキュリティ設計
- マネージドルールはBlockモードで有効にする。Countモードで検知のみする方法もあるが、かりにこの中に不正な通信があり、被害が出る場合を考えると、安全側に倒し、最初からBlockモードで運用する
- ログを取得し、Blockされた通信を確認できるようにすることで、問題が発生した場合にどこで止まっているかを確認できるようにする

### 可用性設計
- マネージドルールを用いて、DDos攻撃を軽減し、アプリケーションの可用性を向上させる

  - 月当たり(時間で換算)$1

  - 月当たり(時間で換算)$10

  - 月1000リクエストと想定
  - $0.6 * 1000 / 100000 = $0.0006
