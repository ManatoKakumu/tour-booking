# Cognito

## 要件・前提
- B側は全パス認証必須、C側は一部パス認証必須
- ユーザープールのみ必須
  - ユーザから直接AWSリソースへのアクセス要件はないため、IDプールは不要
- ALBと同じく東京リージョンに配置する
- ブルートフォース、クレデンシャルスタッフィングへの対処をB・C両方に入れる。Cognito標準機能である段階的ロックアウト、MFA、漏洩認証情報検知にて、補える。ただ、これらは防御のみであり、依然として不正ログインされるリスクがあるので、検知してアカウント利用者もしくは運営に伝えるための手立てが必要

### 選定理由
- 認証ロジックはアプリケーションコードでの実装ではなく、Cognitoを用いる
  - 認証ロジックの自前実装は、意図しないセキュリティホールの発生、開発・テスト・運用コストがかかるなどの観点から、マネージドサービスであるCognitoを用いる
- ユーザープールはB・C側でそれぞれ1つずつ作成する
  - 仮にユーザープールが1つの場合、認証が成功してもそれがB側なのかC側なのか判定がつかず、認証成功か失敗か、でしか判断できないため、C側でログインしてB側のページにアクセスできるリスクがある。そのため、ユーザープールはB・Cでそれぞれ1つずつ作成する
- B・C側ともにPlus tire化する
  - アカウント単位の失敗を追跡することで、ブルートフォースの可能性があることを検知させたい。そのためには、 `userAuthEvents` ログが必要であり、これにはPlus tireが必須なので有効にする
  - なお、クレデンシャルスタッフィングでは特定のアカウントで大量に失敗するような予兆ではなく、多数のアカウントに対して、大量にログイン試行する。これは失敗率が非常に高いと言われているので、全体の失敗率を認知しておく必要があるが、これはPlus tire不要の `SignInSuccesses` にて把握できる
  - Cognitoにはすでに防御の機能が備わっているが、今回検知したいブルートフォースおよびクレデンシャルスタッフィングへの検知機能が標準で備わっていないので、検知機能を別途用意している

### 通信経路
- ALBとCognito間通信
  - 認可コードをトークンに交換する処理が行われる
  - HTTPS通信が必要
- 未認証かつ認証必須の場合、Cognito Hosted UIへ直接アクセスさせる

### セキュリティ設計
- パスワードポリシーはCognitoデフォルトのものを使い、ある程度強度のあるパスワードしか設定できないようにし、パスワード推測のリスクを低減させる
- B側は乗っ取りされた際のリスクが大きいため、MFAを有効にし、アカウント乗っ取りリスクを低減する。C側はCognito Threat Protectionによって、漏洩認証情報によるログインを検知する
- ALBのセッションタイムアウトは6時間とする。数値は仮置きではあるが、短すぎると何度もログインする必要があり面倒、長すぎると逆にログイン後にセッション乗っ取りのリスクがある。間を取り、サービスの特性上、ツアー紹介の設定および参加ツアーを探すのに6時間あれば十分と判断した
  - ALBのセッションタイムアウトである6時間よりも長いので、Cognitoのリフレッシュトークンはデフォルトの30日で問題ない
- 不正ログインと思われる試行が検知された場合は、下記対応をB・C側両方で準備をしておく
  - CloudWatchアラームにて運営に通知する。なお、閾値は仮設定しているが、本来なら、運用してみて、誤検知の割合などを確認したうえで、数値を調整していくのが望ましいと考える。なお、ログイン試行が正規のものかそうでないか、を知る必要があるが、これはユーザーからの問い合わせ（不正ログインについて、など）や、不正ログインの疑いがあったときにユーザーに確認する、などで把握できると考える
  - 検知だけでは、仮にそれが不正ログインだった場合に、対処するまでの間に被害を受ける可能性があるため、Cognitoの適応認証を有効にし、不正ログインのリスクを減らす
- アラーム時の対応について
  - 現状、クレデンシャルスタッフィングもブルートフォースも、それぞれ不正ログインの疑いがある際に、運営に通知されている
  - 不正ログインの疑いがあれば、パスワードの変更やMFA認証（B側は必須だが、C側はない）を要求するのが適切だと思われる
  - しかし、それはユーザーにしかできない操作（運営も行えはするが、パスワードが運営会社の人間に知れ渡る可能性があり、あまり良くない）なので、ユーザーに通知すべきである
  - そう考えると、常に人材は稼働しているわけではない点と、稼働していても運営からユーザーへの通知に時間がかかるので、その間に被害が拡大する可能性もある
  - なので、不正ログインの疑いがあるユーザーにも直接連絡を入れて、パスワード変更やMFA認証を有効にするように促すのが適切と考える
  - ただし、ユーザーに直接送信するには、SES（検証済みメールアドレス）の導入が前提となるので、今回はこれは見送ることにした
  - かわりに、当面の間は、運営への通知による手動で対応し、ユーザーへの通知に遅延が発生することは許容する。不正ログインの疑いが強い場合は、Cognitoに備わっているブロック機能がついていることも、このような判断の一因である
