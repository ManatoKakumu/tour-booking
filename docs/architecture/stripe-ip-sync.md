# Stripe IPリスト同期

## 要件・前提
- ECS(API)が外部API、Stripeを呼びに行く
- セキュリティの観点から、ECS(API)のSGにポート番号443で0.0.0.0/0のルールを追加したくない。仮に侵害された場合に、HTTPS通信であれば理論上、どこにでも通信ができてしまうため。
- 現状、ECS(API)は外部APIとしてStripeしか呼び出さないので、このIPリストに絞ったSGルールを追加したい
- Stripe IPリストはメーリングリストに追加すれば、IPアドレス変更の7日前に通知が来る

## 設計

### 構成図

- [docs/architecture/README.md](README.md)参照

### 選定理由
- Lambdaによる手動実行とする
  - 詳細な比較検討は[docs/adr/005-stripe-ip-sync-trigger-selection.md](../adr/005-stripe-ip-sync-trigger-selection.md)参照
- Lambda選定理由
  - IPリスト変更時のみに実行されればいいので、ECSやEC2ではなく、Lambdaを選択
- 手動実行の選定理由
  - すでにメーリングリストに追加することで、IPリスト変化に対する通知手段が準備されているので、それを改めてこちらで用意する必要性は薄い

### 通信経路
- LambdaからStripe IPリストへアクセス
- Lambdaがプレフィックスリストを更新。プレフィックスリストはECS(API)のSGに付与しているもので、SGの付け替えは発生せず、プレフィックスリストの更新のみでよい
- LambdaはVPC外に置く。LambdaはVPC内部のリソースと通信する必要がない。また、VPC内部に置くと、ENI付与処理など、コールドスタートが発生する可能性が高くなる。そのため、VPC外に配置する

### セキュリティ設計
- 必要最小限の権限を付与する

#### IAMロール
- Lambda
  - `ec2:ModifyManagedPrefixList`, `ec2:GetManagedPrefixListEntries` を特定のプレフィックスリストのARN指定をする
  - `ec2:DescribeManagedPrefixLists` はARN指定ができないので、Resourceは `*` とする

### 可用性設計
- 処理失敗時の通知手段は設けない。これは手動実行によるものなので、実行させた際に結果が確認でき、仕組みとして導入するメリットがあまりないと判断した
- 同時最大実行数は1としておく。手動オペレーションとはいえ、複数人が同時に実行した際にプレフィックスリストの競合が発生するのを懸念し、1とする

### コストの見積もり・意識した点
- Lambda
  - リクエスト数
    - 100万回/月までは無料。どれくらいの頻度でStripe IPアドレスが変更されるかはわからないが、月に一度あるかないか程度だと想定。ECRライフサイクルポリシーでもLambdaを使ってはいるが、それを合わせても100万回/月には及ばないと想定し、$0とする
  - 実行時間
    - 40万GB秒/月までは無料
    - プレフィックスリストの更新処理はそこまで重い処理ではないと想定。また、月に一度あるかどうか程度の頻度と想定される
    - 実行時間は、Stripe更新処理があるので、長めに見積もり、100秒と想定
    - 1回 * (128/1024) * 100秒 = 12.5GB秒
    - ECRライフサイクルポリシーと合計しても40万GB秒/月には達しないと想定し、$0とする
