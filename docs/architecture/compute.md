# コンピュート層

## 要件・前提
- フロント・API、B・Cで分離し、全部で4種のコンテナがある
- OSなどを柔軟にカスタマイズしたい要件がないため、コンテナの起動タイプはFargateとする
- ALBを用いたパスベースによるルーティングで各種コンテナにルーティングさせる
- Cognitoによる認証付きが必須となるURLと、認証不要のURLが存在する
- DBユーザはAPIのB・Cでそれぞれ作成し、それぞれ必要になるテーブルのみに絞った権限を付与する。フロントからのDBアクセスは許可せず、APIを経由するものとする。ただし、今回のセッション時点では実テーブル(スキーマ)がまだ存在しないため、RunTaskでの実装は`CREATE USER`まで(パスワード設定込み)にとどめ、`GRANT`はスキーマ(マイグレーション)が実装されたタイミングで別途対応する
- フロントはブラウザ経由でAPIから直接データを取得させる形とし、フロント→APIのサーバー間通信経路は設けない
- SEO(LCPが悪化する)への影響は認識したうえで、CSRとする。実集客が必要になった場合はSSRを検討する。仮にSSRにした場合、フロント→API間の同期呼び出しでAPIの遅延がフロントを巻き込むことになる。この結合を避けるため、現段階ではCSRを選ぶ
- DBユーザの認証情報はSecret Managerに保存し、Secret Managerと通信するためのVPCエンドポイントを作成する
- オートスケーリングをおこない、無駄なタスクの排除によるコストの最適化、およびリクエスト急増時にレイテンシを悪化させないようにする

## 設計

### 構成図
- [docs/architecture/README.md](README.md)参照

### 選定理由
- FargateタスクのCPU
  - 256(0.25 vCPU)
- Fargateタスクのメモリ
  - 512MB
- CPUおよびメモリは最小サイズとする
  - 現状はトラフィックがほぼなく、負荷が小さいことが想定されるため、コスト抑制のため、最小サイズとする
  - ただこの決定自体は、後からサイズを変更するのが容易、ダウンタイムが少ない、という前提のもと行った判断である

### 通信経路
- ALB → Cognito → ALB → ECS(パスベースルーティング)
- ECS API → Secret manager → ECS API → RDS
- ECS RunTask → Secret manager → ECS RunTask → RDS

### オートスケーリング設計
- フロント・APIそれぞれでスケーリングポリシーを検討する

#### フロント
- スケーリングポリシーを `タスク1台あたりのALBリクエスト数` をポリシーにする
- フロントが返すページが動的ページであっても、DB参照部分はブラウザが別でAPIにリクエストを飛ばす流れになっている。そのため、フロントはCPU使用率やメモリ使用率が高くなることはないと思われる
- そのため、実際の需要を直接表すリクエスト数に応じて、スケーリングすべきであると判断した
- ターゲット数値は、今の段階で適切に決めることはできない。負荷試験を行い、スケーリングをしたほうが良いであろう数値を計測し、その数値より少し手前に設定する。このようにすることで、CloudWatchアラームが検知+インスタンスの起動時間によって新規追加したインスタンスがリクエスト処理できるまでにかかる時間も考慮した、本当にスケールアウトさせたいタイミングに近づけて起動させることができると思われる。今回は仮で数値は `100` とするが、暫定である

#### API
- ツアー紹介および予約を管理するアプリケーションで、主にDBへの参照処理が多いと思われる
- そのため、スケーリングポリシーを `タスク1台あたりのALBリクエスト数` をポリシーにする
- I/O待ちが主体かと思われるので、CPU使用率やメモリ使用率とレイテンシの関連が薄いと思われる。一方で、アクセスが集中する時がスケーリングすべきタイミングと判断
- 数値は `100` とする。理由などはフロントと同じなので、記載はしない

#### 最小・最大タスク数
- この設定はフロント・API同じとする
- スケーリングポリシーと似たような話だが、実際に運用して負荷状態を計測して数値を決めるべきだと思うので、ここでは仮の数値を決める。特に、最大タスク数は、数か月程度運用し、その中での一番多かったリクエスト数/分に耐えられると思われるタスク数を設定するのがよいと考えている
- 最小タスク数は2とする。これはマルチAZ構成にすることで、可用性を向上させることを目的とする
- 一方で、最大タスク数は決められる状態にないので、3とするが、暫定である

### セキュリティ設計
- Secret Managerで認証情報を管理することで、認証情報を自動ローテーションし、長期的な認証情報を用いない
- Cognitoによる認証を必須(一部パスを除く)とすることで、認証必要なページへのアクセスを制限する
- DBユーザをB・Cで分離することで、不必要なテーブルへの権限をそもそも与えないようにする。IAMをB・Cでそれぞれ作成し、Secret Managerから必要な認証情報だけを取得できるように絞り込む
- コンテナ分離することで、仮にAPI-Cのコンテナが侵害されても、API-B側で書き込みの行えるテーブルにまで影響を与えないようにする。ただし、同じプログラミング言語を用いた開発・似たようなDockerFileになることが想定されるので、同じ手口で侵害される可能性があることは注意する必要がある

### 可用性設計
- ECSタスクの `desired_count` を2以上とすることで、マルチAZ構成で起動されるようにし、可用性を向上させる
- VPCエンドポイントはAZに1つずつ作成し、シングルAZ障害時にもSecret ManagerからDBユーザの認証情報を取得し、DBとの通信を遮断される確率を下げる

### コストの見積もり・意識した点
- ECS
  - 最小・最大タスク数で起動するコストを出し、ざっくりと範囲でみつもる
  - vCPU
    - $0.05056/h
    - 最小： 4 * 2 * 730h * 0.05056 * 0.25 = $73.8176
    - 最大： 4 * 3 * 730h * 0.05056 * 0.25 = $110.7264
  - メモリ
    - 0.00553/h/GB
    - 最小： 4 * 2 * 730h * 0.00553 * 0.5 = $16.1476
    - 最大： 4 * 3 * 730h * 0.00553 * 0.5 = $24.2214
  - 合計
    - 最小： $73.8176 + $16.1476 = $89.9652
    - 最大： $110.7264 + $24.2214 = $134.9478
- Secret Manager用のVPCエンドポイント
  - $0.014/1h
  - 各AZに1つずつ作成する
  - $0.014 * 730 * 2 = $20.44
  - 合計$20.44
- 合計
  - 最小：$89.9652 + $20.44 = $110.4052 
  - 最大：$134.9478 + $20.44 = $155.3878
