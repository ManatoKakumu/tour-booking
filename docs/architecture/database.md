# DB

## 要件・前提
- RDSが記載対象
- リレーショナルデータベース、MySQLを選択
- マルチAZ構成で可用性を確保する
- 必要な通信は、ECS(API)からの読み取り・書き込み、およびプライマリ・スタンバイ間のレプリケーション処理
- B・C間でDBユーザー、GRANT権限を分け、それぞれのユーザーがいじる必要のないテーブルの参照および書き込みを許容させない
- ECS(API)は読み込み・書き込みを行う
- RPOは5分、RTOは1時間、スナップショットの保持期間は7日とする。

### RPO/RTO/スナップショットの保持期間について
- 今回は、DR計画については実装はせず、ドキュメントで計画方針について残すのみとする。実装まで行う範囲では、AZ範囲でのデータ損失、人為的ミスによるデータ破損を対象とする(マルチリージョンDRの検討・不採用理由は[ADR-006](../adr/006-multi-region-dr-scope.md)を参照)

#### RPO
- RDSのポイントインタイムリカバリのデフォルト間隔が5分で、追加の投資なしに実現できる数値なので、今回は5分とした
- 本来であれば、下記の観点から、トレードオフで決めたほうが良いと考えている
  - データの重要度に応じて決める。例えば、データ損失が許されないような金融データなどはRPO0分、多少のデータ損失が許される社内システムなどはRPO数時間、重要度の低い一時データなどは1日など、のように決める
  - コストの観点も考慮する。RPOが短くなるほど、頻繫にスナップショットを取得する必要がある。また、保持するデータ量が増えるので、コストも増加していく
  - 今回は、旅行決済処理データがあるので、これは失うと利用者にとって損失を被るので、RPOは0分に近づけるほど良いと思われるが、その分、RPO0分を実現するためのコストがかかり、仕組みの導入が必要となる。仮にAZ障害側のRPOを0分に近づけたいなら、RDSは既にマルチAZ構成で同期的にレプリケーション処理を行っているため、この要件は既に満たしている。リージョン単位で考慮すると、Aurora DSQLがあり、これは今回のRDSからの移行に大きなアーキテクチャ変更を伴わない点で、現実的な方法であると考える

#### RTO
- 障害が発生した際に、どの時点まで戻ってデータを復元するか、これは自動化ではなく、人が判断する必要がある。その後、手動で復元することを考慮すると、1時間程度と想定し、RTOを1時間とした
- そもそも、障害をどのように検知するかは、今後検討する
- 本来であれば、下記の観点からRTOを決定するべきであると考える
  - 事業停止がどれくらい許容されるかを決める。例えば、電気水道ガスなどのインフラであれば、かなり短くなるだろうが、今回のように旅行は別に行けなくても大きな問題にはならないので、長めにとることも許容されやすいと考える
  - 実際のデータ量に基づき、定期的にスナップショット復元テストを行い、復元にかかる時間を把握する。かりに復旧時間が、許容時間に間に合わなければ、DBの性能向上なども考慮に入れる
  - スナップショットの復元テストは、7分程度で完了。ただし、データ量が増えるにつれ、時間は増加していくであろうことは考慮する必要がある

#### スナップショットの保持期間
- 障害が発生した際に、7日あれば気づいて対応まで完了できる、特に法的要件でデータ保持期間を決められているものでもないので短めに設定する

### 通信経路
- ECS(API)からのリクエスト
- プライマリ・スタンバイ間のレプリケーション処理
  - ただし、これは設定するだけで特に通信処理を自身で設定管理する必要はない
- DBサブネットはlocalのみ（明示的な追加不要）で、外部への経路を一切持たない

### セキュリティ設計
- ECS(API)からのリクエストはECSおよびRDSに付与するSGによって許可する
- B・Cユーザがそれぞれ参照する必要のあるテーブルだけに権限を絞ったDBユーザを各自用意する。API-B, API-Cは読み込み・書き込みを行うが、必要なテーブルにしか権限を持たないようにDBユーザーを2種類(API-B, API-C)作成する。認証情報はSecret Managerを用いる
- データは暗号化して保存するが、転送中の暗号化は行わない
- RDSのパブリックアクセスはブロックし、ECSのみから受け付けるようにする
- deletion_protectionはfalseとする。本来なら誤削除防止のためtrueにすべきだが、今回は個人開発でコスト優先のため、terraform destroyしたら削除されるように、falseとする

### 選定理由
- DBエンジンの選定(RDS vs Aurora)は[ADR-003](../adr/003-rds-vs-aurora-selection.md)を参照
- Secret Managerは認証情報を自動でローテーションするため、仮に漏洩しても長期間に渡る不正アクセスの可能性を下げることが可能
- 保存時は暗号化を必須にすることで、仮にスナップショットが漏洩しても暗号化されているため、情報流出のリスクを下げることができる。スナップショットはIAM権限さえあれば取得できるため、注意する必要がある。なお、暗号化はKMSではなくデフォルトのキーを用いて暗号化する。今回は、誰が複合化したかを知りたい監査的要件がない、一部の人だけに複合化を許可したいユースケースがない、以上から、デフォルトキーを用いた暗号化とし、金銭的コストを抑える
- 転送時には暗号化をしない。転送時の暗号化で防げることは、通信を盗聴された際であるが、そのようなケースは今回の構成において想定したのは、ECSタスクが侵害される場合のみである。ECSタスクが侵害されていれば、DBの認証情報を得てリクエストが可能なので、転送時に暗号化をしても情報を流出できることはない。以上より、転送時の暗号化で守れるケースは少ないと判断し、行わないこととした。
- インスタンスクラスは `db.t4g.micro` とする
  - ストレージとコンピュート層は独立しているため、インスタンスクラスの変更はストレージに悪影響をあたえない
  - マルチAZ構成であるため、インスタンスクラスののちの変更でもダウンタイムは数分程度に収まる想定なので、のちの変更が致命的にはならない
  - 負荷の強さが低い(t3/t4g, micro)、料金が低い(t4g)、という観点でインスタンスクラスを決定
- ストレージタイプはgp3とする
  - 大規模OLTPなどのように高いIOPSを求めているわけではない
  - ストレージ容量は最小制約20GBと想定する。仮にストレージ容量が不足しても自動で拡張してくれるので最初から余裕を持たせる必要はない

### 可用性設計
- マルチAZ構成により、可用性を向上させる
  - AZ障害時にも自動でフェイルオーバーするため、ダウンタイムを最小限に抑えることができる
  - エンドポイントは変わらないため、手動での変更は不要
- RPO5分は、RDSのポイントインタイムリカバリを用いて実現する
- backup_retention_periodは7日とする

### コストの見積もり・意識した点
- Secret Manager
  - フロント・API共にB・CでDBユーザーを分けたほうが、想定外のDB値参照・更新を防げるので、それに伴い、シークレットは4つ作成する。別途管理ユーザの認証情報も保存する
  - 10,000件のAPIコールあたり$0.05
    - $0.05と想定
  - 1シークレットあたり$0.40/月
    - $0.40 * 2 + $0.40 = $1.20
  - 合計$1.25/月
- RDS
  - インスタンスクラスは `db.t4g.micro`
    - $0.05/1h
    - $0.05 * 730 = $36.5
  - ストレージタイプは `gp3`
    - $0.276/GB/月
    - $0.276 * 20 = $5.52
  - 合計$42.02/月
- バックアップ料金
  - 現在のデータ量は個人開発で、自身以外からのリクエストはほぼ0なので、データ量はかなり少ない
  - バックアップ保持期間は7日
  - これらを考慮すると、20GBに達することもないと思われるので、$0と想定
- 合計$43.27/月
