# S3(静的配信)

## 要件・前提
- ユーザーがアップロードする画像を保存するS3バケットと、静的ページ(会社概要ページなど)を配信するページを格納するバケットを2つ用意する
- 2つのバケットともに、バージョニングを有効にして、仮にデータが削除されても復旧できるようにしておく
- 画像保存バケット
  - アップロードはECS(API)経由のみ
  - 読み取りは、CloudFront経由のみ(OAC)
- 静的ページ保存バケット
  - アップロードは特定の開発者のみ
  - 読み取りは、CloudFront経由のみ(OAC)

## 設計

### 構成図

- [docs/architecture/README.md](README.md)参照

### 選定理由
- 画像保存にS3を選んだのは、非構造データに対応していること、および今後大量の画像がアップロードされた際のコスト効率が良いため。また、ECS(フロント)がS3から画像を取得し、それを埋め込んだページを返す方式にすると、レイテンシ増加になるので、画像取得とページ取得をそれぞれ分割した経路とした
- 静的ページにS3を選んだのは、サーバー管理が不要、および会社概要ページなど絶対に配信を止めてはいけない重要データを高い耐久性で保持したいため
- S3バケットを2つ用意しているのは、セキュリティ的な観点からである。仮にS3バケットを1つにすると、ECS(API)がそのS3バケットへのPutObject権限を持つことになり、会社の静的ページを上書きできる可能性がある。でも、静的ページは本来、ユーザには一切触らせる必要がないので、このようなリスクを根本的になくしたい。そのため、S3バケットを分けることで、ECS(API)に静的ページを上書きできる可能性を潰すことを目的に2つに分割した

### 通信経路
- 画像保存バケット
  - アップロード：ECS(API)→S3バケット
  - 読み込み：CloudFront→S3バケット(OAC)
- 静的ページ保存バケット
  - アップロード：開発者→S3バケット
  - 読み込み：CloudFront→S3バケット(OAC)

### セキュリティ設計
- 画像保存バケット
  - PutObject：Resourceはバケット全体に、ECS(API)に付与するIAMロールのARNのみを許可する
  - GetObject：Resourceはバケット全体に、特定のCloudFrontのARNのみを許可する(OAC)。パブリックアクセスはブロックする
- 静的ページ保存バケット
  - PutObject：Resourceはバケット全体に、開発者用IAMロールのARNのみを許可する
  - GetObject：Resourceはバケット全体に、特定のCloudFrontのARNのみを許可する(OAC)。パブリックアクセスはブロックする

### 可用性設計
- 特にこちら側で準備できることはない

### コストの見積もり・意識した点
- ストレージ料金
  - 最初の50TB/月は$0.025/GB
  - 少し多めに見積もり、画像保存バケットおよび静的ページ保存バケットの合計容量は10GB(現時点の想定)とする
  - 10GB * $0.025 = $0.25
- リクエスト料金
  - PUT：1000リクエストあたり$0.0047
  - GET：1000リクエストあたり$0.00037
  - PUT, GETともに500リクエスト/月と想定
  - $0.0047 / 2 + $0.00037 / 2 = $0.002535
- 合計$0.252535
