# アプリケーションコード CICD

## 要件・前提
- ディレクトリ構成はフロント・API、B・Cで分離する4構成とする。これらに共通コードはない。
- イメージタグはイミュータブルでECRに保管する
- デプロイ方式はローリングアップデートとする
- Terraformとの境界: タスク定義の型(CPU/メモリ等)はTerraform、イメージタグの更新はCI/CD。Terraform側で`lifecycle { ignore_changes }` を設定し、インフラ変更のapplyでイメージタグが巻き戻らないようにする
- DBユーザーの作成は、ECS構築後に、APIのOIDC権限を使った一度きりのECS RunTaskで実行する想定。workflow_dispatchによる手動トリガーとし、pushでは動かない。

### 選定理由
- 4つにビルドを分けるのは、ビルドの無駄を省くため
  - 例えば、フロントB側のUIだけを変更したい場合に、APIやフロントC側は一切影響がないのにそれらもビルドする無駄を省きたいため
  - 実現方法としては、pathsフィルターでトリガーする
- イミュータブルでイメージタグを保存するのは、仮にイメージに問題があった場合に、即座にロールバックをできるようにするため
- ローリングアップデートとしたが、永続的ではなく、運用していく中で必要に応じてBlue/Greenアップデートなどに変更することも見越している
  - 新旧バージョンが混在してもそれが問題になるユースケースの想像がつかなかった（ただし、現段階での話ではあるが）
  - 一時的とはいえ、コンテナが2倍になるので、コストが高くなる
  - 仮にBlue/Greenアップデートに移行したい場合、ターゲットグループを4個(フロント・API、B・C)追加する、など比較的容易に完了する見込みなので、初期段階から固定する必要はない
  - `minimumHealthyPercent` の設定に気を付け、仮に新イメージに問題があった場合に全滅しないように注意する

### ビルド条件
- PR作成・更新時に、pathsフィルターでビルドおよびテストを走らせ、問題がないか確認する
- mainへのマージ時に、同様にビルドし、ECRへプッシュする

### stateレイヤー配置
- ECRリポジトリ4個
  - コンピュートB・Cレイヤーにそれぞれ配置
  - ECSはECRが存在しないと起動できない依存関係、両者の変更頻度はそこまで高くないと想定されることから、ここに配置。なお、アプリケーションコードの更新とstate更新は分離されているので、stateの更新頻度は近しいと想定
- IAM Role
  - コンピュートB・Cレイヤーにそれぞれ配置
  - これもECRリポジトリと同じ理由にて配置場所を決定
- OIDC Identity Provider
  - `network-sg-alb` レイヤーに追加
  - このレイヤーは、他のサービスが依存する、という既存の役割、および更新頻度がSGなどと近い、と判断し、このレイヤーに配置

### イメージスキャン
- 基本スキャンとする
  - 基本スキャンはプッシュ時や手動などのみ、かつOSの基本的な脆弱性スキャンにとどまる
  - 一方で、拡張スキャンはOS+プログラミング言語の脆弱性スキャン、および脆弱性DB更新時にもスキャンが走るので、イメージのプッシュにかかわらず、最新の脆弱性検知が可能になる。セキュリティ的な観点からは、拡張スキャンが望ましいと思われる。
  - ただ、これは個人開発で公開される予定もないので、コストを無料に抑えるために基本スキャンとする。なお、拡張スキャンに変更したくなった場合も、設定はかなり簡素に終わるので、問題ない認識

### イメージのライフサイクルポリシー
- イメージが蓄積されていくとストレージ料金がかかる。とはいえ、仮にイメージに問題があって起動できなかった場合に即座にロールバックさせたいため、消しすぎもよくない
- 方針として、ECSのデプロイ完了イベントをトリガーに、Lambdaがヘルスチェック結果を見て、タグを付け替える。起動成功タグは90日間、失敗タグは30日間、など成功タグは長めに設定し、期間が過ぎたら削除されるようにする方針（数字に根拠は全くなし）。なお、ECRはどのイメージタグがECSで使われているかを知らないので、それをタグ名で伝える必要があり、現在動いているタグには `current` とつけ、新規の `current` が作成されたら、過去のタグを `検証済み` タグに付け替えて、日数経過後に適切に削除されるようにする必要がある。なお、コンピュート層構築後に実装する

### セキュリティ設計
- AWS認証はOIDC連携を用い、長期的な認証情報を持たないようにする
  - 一時的な認証情報とはいえ、漏洩すれば、そのロールで許容されていることがすべて実行できてしまう。なので、ECRリポジトリへのpushのみ、というロールを4リポジトリ分作成し、仮に漏洩しても1リポジトリにしか被害が及ばないようにする。

### 可用性
- GitHub ActionsはGithub側のSaaSで、可用性はGitHubが責任を持ち、自分で考慮する必要はない
- ECRも同様に、可用性はAWSが責任を持つ
- 仮にGitHub ActionsやECRが止まっても、稼働中のコンテナは止まらない
- 不適切なイメージがプッシュされ、そのイメージでコンテナがデプロイされるのを防ぐ方法として、下記がある
  - GitHub Environmentsのrequired reviewers機能で承認ゲートをはさむ
  - CodePipelineを構築し、ビルドやテストのステージの後に自動承認プロセスを挟む、かつ承認できる人をIAMで絞る。ただし、これはGitHub ActionsでCICDを組む前提の場合には大きな構成変更となり、あまり望ましい手段とは言えない
  - ただ、今回は個人開発なので、安全性を高めるデプロイ手法は対象外とする
