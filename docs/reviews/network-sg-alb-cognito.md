## 観点別レビュー

### 設計

- 4ファイルへの分割は、tfstateのレイヤー分割(ネットワーク+SG+ALB)とは独立して「サービス単位」で行っており、ドキュメントとしての読みやすさを優先した判断が一貫している
- `network.md`の通信経路→選定理由の順序入れ替え(サブネット構成を先に説明してから、その上でIGW/NAT/VPCエンドポイントの理由を展開する)は、依存関係を意識した良い構成
- 各ドキュメントで「書くことがない節は削る」判断を繰り返しており(対応Step、実装、わからなかったこと、可用性設計、コスト等)、テンプレートに引きずられず対象の実態に即して構成している

### セキュリティ

- 3階層(Public/Private-NAT/Isolated)のルートテーブル + SG + Cognito User Pool分離 + DB権限分離、と複数レイヤーで多重防御になっている
- VPCエンドポイント採用の理由が「侵害されたECSからの情報持ち出しを、NAT Gatewayの出口を絞ることで抑える」という具体的な脅威モデルに基づいており、説得力がある
- ALBを論理的に1つにする判断で、当初「Cognito認証が侵害時の被害限定の代替になる」としていた誤った理由付けを、「ALBはステートレスで認証情報を持たないため分離の効果がない」という正確な理由に修正できている。これは脅威モデル(外部からの不正アクセス防止 vs 内部からの侵害後の被害限定)を混同しない、という重要な区別ができている証拠
- **抜け(構築フェーズで対応)**: Cognito App Clientのシークレットの保管方法がどこにも書かれていない。Terraform管理下に平文で置かない(Secrets ManagerまたはSSM Parameter Store経由にする)という方針は、実装レビューの際に確認する

### 可用性

- 2AZ構成の理由(ALB/RDS Multi-AZが元々プライマリ+スタンバイの2ノード構成であること)を明示しており、「予算があれば3AZの方が良い」という誤読を避けられている
- NAT Gateway Regional modeの制約(プライベート接続非対応)と、今回それが問題にならない理由の両方が書かれている。トレードオフを両論併記できている
- ALB・Cognitoはフルマネージドサービスであり、可用性設計として書くべき固有の判断がないと判断して節ごと省略した点は妥当

### 運用性

- NAT Gatewayのegress制限を支えるStripe IPプレフィックスリストの同期(EventBridge+Lambda)は、方針レベルで記載しつつ、実装の詳細と着手タイミングを明確に持ち越し事項として区別できている
- ElastiCacheのB/C未分離という既知のギャップを、対応範囲外と自覚した上で意図的に保留しており、記録にも残している。これは「気づいていない」のと「気づいた上で優先度を下げた」の違いが明確でレビューしやすい

### 保守性

- SGをCIDR指定ではなくSG参照にする理由(ECSのIPアドレスがスケーリングで変動するため)が明記されており、将来の変更に強い設計になっている
- NAT Gatewayのegress制限を、SGのルールとして表現する(NAT Gateway自体にはSGを付与できない、という誤解も途中で訂正済み)、という正しい理解に基づいている

### コスト

- NAT Gateway・VPCエンドポイント・Cognitoのいずれも、AWS公式の料金ページを実際に参照して数値を検証しており、見積もりの信頼性が高い
- **改善余地**: 4ファイルそれぞれに個別のコスト記載はあるが、この範囲(ネットワーク+SG+ALB+Cognito)全体の合計金額がどこにもまとまっていない。必須ではないが、`docs/architecture/README.md`か、いずれかのファイルに合計を一言記載すると、全体感が伝わりやすくなる

### パフォーマンス

- VPCエンドポイント経由の通信、ALBのマネージドスケーリングなど、現状の想定トラフィック規模ではボトルネックになりそうな設計判断は見当たらない
- 現時点でパフォーマンス要件が明文化されていないため、この観点は「懸念なし」であって「十分に検証済み」ではない。実トラフィックが発生した後に再評価する対象

### Terraform化した場合の改善点

- SGはSG参照ベースで設計されているため、Terraformでも`aws_security_group_rule`の`source_security_group_id`を使う実装と自然に対応する
- ALBの`session_timeout`・Cognitoのトークン設定は、`aws_lb_listener_rule`の`authenticate_cognito`ブロックのパラメータとして素直にマッピングできる
- backend設定は既存のADR-002方針(部分バックエンド設定、AWSアカウントIDを`.tf`に含めない)を、このレイヤーでも徹底する

### AWS Well-Architected Framework 6本柱

- 運用上の優秀性: NAT Gateway/VPCエンドポイントの選定理由が明文化されており、変更理由の追跡がしやすい。監視・アラートの設計はまだ範囲外(後続フェーズ)
- セキュリティ: 多層防御(ルートテーブル・SG・Cognitoプール分離・DB権限)が一貫した原則で設計されている。App Clientシークレットの管理方法のみ未定
- 信頼性: マルチAZ・Regional NAT Gateway・フルマネージドサービス(ALB/Cognito)の活用により、可用性の設計判断は妥当
- パフォーマンス効率: 現状のトラフィック規模を踏まえると過不足のない構成。将来の見直し前提
- コスト最適化: すべての見積もりが一次情報に基づいており、コストとセキュリティのトレードオフ(VPCエンドポイントの追加コストを受け入れる判断など)が明確
- 持続可能性: 直接的な観点での言及はないが、フルマネージドサービス中心の構成により、自前でのリソース過剰プロビジョニングは避けられている

### 実務ならどう設計するか
