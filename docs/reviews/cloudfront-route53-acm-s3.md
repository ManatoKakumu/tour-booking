セキュリティ設計では、画像バケットへのPutObject制限を「VPCエンドポイント経由のみ」というネットワーク経路の制限だけで済まそうとした場面がありましたが、指摘を受けて「IAMロールによるアイデンティティの制限」が本質的に必要だと正しく理解し直せました。これは実務でもよくある混同(経路の制限とアイデンティティの制限は別物)で、区別できるようになったことは大きな収穫です。

## 観点別レビュー

### 設計

- CloudFrontの3分岐ルーティング(画像/静的ページ/動的ページ)が、S3(2バケット分離)・ALB(VPC Origins)の設計と矛盾なく対応している
- 当初「`static`で始まるパス」という曖昧な条件だったキャッシュビヘイビアを、実際のトップページ(`/`)がカバーされないという問題に自分で気づき、`/`, `/about`, `/terms`という具体的な列挙に修正できた。「デフォルトを動的側のままにし、少数派の静的ページ側を列挙する」という判断も、実際のパス数の非対称性(静的3つ・動的多数)を踏まえた合理的な選択
- 「1ドメインを複数のCloudFrontディストリビューションにパスベースで分割できないか」という本人からの鋭い疑問は、DNSがパス情報を見られないこと、CloudFrontのカスタムドメインが1対多の関係にしかならないこと、という2つの技術的制約で正しく説明・解消された

### セキュリティ

- S3画像バケットのPutObject制限について、当初「VPCエンドポイント経由のみ」というネットワーク経路の制限のみだった設計を、「ECS(API)に付与するIAMロールのARNのみ許可」というアイデンティティベースの制限に正しく修正できた。同じVPCエンドポイントを他のリソース(ECS フロント等)も使う可能性がある、という抜けを認識できたのは良い判断
- パブリックアクセスブロックが当初抜けていたが、指摘後に画像・静的ページ両バケットへ追加できた。OAC単体では防げない「バケットポリシーの誤設定」という別の脅威に対する多層防御の意味を理解できている
- CloudFront側のセキュリティ設計(AWS管理のCloudFront-VPCOrigins-Service-SGをALBのSGで参照する)は、`network-sg-alb-cognito`レビュー時点の持ち越し事項をそのまま解消する内容になっており、過去の記録との接続ができている
- ACMの秘密鍵管理について、「自己署名証明書の秘密鍵はtfstateに平文で残る」という過去の自分たちの実装上のリスクを踏まえ、「ACMは秘密鍵を外部に一切渡さない」という利点を正しく言語化できた
- Route53のセキュリティ設計(ホストゾーンの変更権限をIAMで自分のみに絞る)、DNSSEC見送りの判断はいずれも妥当。DNSSEC見送りの理由が、当初「ドメインの知名度」という技術的に的を外した理由だったが、指摘後に「実トラフィックが無い段階ではリスクが顕在化する具体的な場面が無い」という、このプロジェクトで一貫している判断パターン(ElastiCache不採用等と同じ)に言い直せた

### 可用性

- S3・CloudFront・ACMはいずれも「フルマネージドサービスで、追加の可用性設計は不要」という判断で一貫しており、過去のALB/Cognitoの扱いとも整合している
- Route53については、「可用性設計の余地が無い」のではなく「ヘルスチェック+フェイルオーバールーティングという機能自体は存在するが、DR計画が無い現段階では使わない」という、より正確な理由に修正できた。これはStep9への持ち越しとも整合する

### 運用性

- `network-sg-alb-cognito`レビューで持ち越しにしていた項目(ALB向けCloudFrontのSG許可、S3画像用バケットへのVPCエンドポイントポリシー、ALB証明書の自己署名からの置き換え)が、このドキュメント群の中で扱われ、行き場を失っていない

### 保守性

- 4ファイルへの分割(サービス単位、tfstateレイヤーとは独立)が、Step2〜4のときの判断パターンを踏襲できている

### コスト

- 全体を通じて、単位の取り扱い(「1,000リクエストあたり」の価格を実際のリクエスト数に正しく反映させる)でミスが複数回発生した(S3のリクエスト料金計算で、500リクエストに対して1,000リクエスト単価をそのまま掛けてしまうミスが2回)。いずれも指摘後に自力で気づき修正できているが、単位を意識する習慣は今後も注意が必要
- Route53のDNSクエリ費用について、当初「ALIASレコードは無料」という情報と「DNSクエリ費用を一律計算する」という記述が矛盾したまま残っていたが、指摘後に「訪問者からのアクセスはALIASなので無料、標準レコード(ACM検証用CNAME)への問い合わせのみが課金対象で、これは低頻度」と正しく整理できた
- 最終的な合計金額は、CloudFront $0、S3 約$0.25、ACM $0、Route53 $0.5程度で、全体として月1ドル未満に収まる見積もりになっている

### パフォーマンス

- 画像・静的ページをS3から直接配信し、ECSを経由させない設計により、計算不要なコンテンツに余計な処理層を挟まない、という判断が選定理由にも明記されている

### Terraform化した場合の改善点

- 新しいtfstateレイヤー(`infra/cloudfront-route53-acm-s3/`、既存のstate分割方針「CloudFront/Route53/ACM/S3(静的配信)」に対応)を新規作成することになる
- ACMがus-east-1(CloudFront用)とap-northeast-1(ALB用)の2リージョンにまたがるため、**このプロジェクトで初めてprovider aliasを使った複数リージョン管理が必要になる**。`provider.tf`でのエイリアス定義、各リソースでの`provider =`指定を漏れなく行う必要がある
- `infra/network-sg-alb/`側への書き戻しが必要な作業がある: ①`security_group.tf`へのCloudFront-VPCOrigins-Service-SG参照追加、②`acm_temporary.tf`(自己署名証明書一式)の削除とALBリスナーの`certificate_arn`差し替え。これらは今回のレイヤーの構築と同時並行で行うことになるため、依存関係(先にCloudFront側のACM証明書・VPC Origin設定ができてから、network-sg-alb側を更新する順序)を意識する必要がある
- CloudFrontの`ordered_cache_behavior`は、リストの順序が優先度を意味する。`/`, `/about`, `/terms`, `images`から始まるパスをそれぞれ個別のビヘイビアとして定義し、デフォルト(`*`)をVPC Origin(ALB)に向ける実装になる

### AWS Well-Architected Framework 6本柱

- 運用上の優秀性: 過去の持ち越し事項が、依存先のレイヤーが実際に構築されるタイミングでまとめて解消される、という一貫した運用方針が保たれている
- セキュリティ: OAC+パブリックアクセスブロックの多層防御、PutObjectのIAMロール限定、ACMの秘密鍵非公開、CloudFront VPC OriginsによるALB完全プライベート化、と一貫した最小権限・多層防御ができている。DNSSECは「検討したが見送り」という判断が明文化されている
- 信頼性: フルマネージドサービス中心の構成で、可用性設計の懸念は小さい。DR・フェイルオーバーはStep9に一貫して持ち越されている
- パフォーマンス効率: 計算不要なコンテンツ(画像・静的ページ)をアプリケーション層から切り離す設計ができている
- コスト最適化: 月1ドル未満に収まる見積もり。CloudFrontの新料金体系(バンドルプラン)を発見・確認し、既存設計への影響がないことを確かめられた
- 持続可能性: 特筆事項なし

## 理解できていること

- OAC(S3向け)とVPC Origins(ALB向け)の使い分け(オリジンがVPCの内部にあるかどうかで、使う機構が変わる)
- CloudFrontのキャッシュビヘイビアが「デフォルト(`*`)+優先度の高い具体的なパスパターン」の組み合わせで構成されること
- Route53が実際のトラフィックの経路には入らず、DNS名前解決のみを担うこと(お名前.comも同様に、NS委任という設定時点の作業であり、経由地ではないこと)
- CNAMEレコードがルートドメインで使えない理由(SOA・NSレコードとの共存不可)と、ALIASレコードがそれを回避できる理由
- ネットワーク経路の制限(VPCエンドポイント条件)と、IAMロールによるアイデンティティの制限が別物であること
- ACMの秘密鍵がAWS内部で管理され、外部に一切エクスポートされないこと。これが自己署名証明書(tfstateに秘密鍵が残る)と比べた際の本質的なセキュリティ上の利点であること

### 実務ならどう設計するか

- 「循環依存に気づいたら、まず橋渡し(一時的な回避)で凌ぐか、それとも境界(モジュール・state・サービスの分割線)自体を見直すか」を都度判断する必要がある、という実務でも頻出する場面を経験できた。今回は「証明書は境界の見直しで解消、SGルールはAWSの仕様上どうしても残るので橋渡しを恒久的に許容する」という、性質の異なる2つの依存を区別して使い分けられたのが良い判断
- レビュアー(Claude)側の見落とし(`network-sg-alb`との循環依存を事前に洗い出せていなかった)を、本人が的確に指摘して正させた場面があった。実務のコードレビューでも、レビュアーの意見を鵜呑みにせず、自分でも依存関係を検証する姿勢は重要
