## 総評

良い出来です。特に、検討の過程で「フロントはDBに直接アクセスすべきか」という、既に完了扱いだった`database.md`・`security-group.md`の前提そのものを問い直し、B/C分離の実効性(GRANTだけでは守れない行単位の隔離を、アプリケーション層のWHERE句に一本化する)という一貫した論理で結論を出し、実際に既存レイヤーまで遡って修正できた点が優れています。CSR/SSRの判断でも、一度出した結論(CSR)を「妥協ではないか」と自ら疑い、LCP/CLSの技術的な区別まで踏み込んで再検証し、最終的に「フロント→API間の同期結合がノイジーネイバー対策の原則と逆行する」という、このプロジェクト独自の設計原則に基づいた結論に到達しています。ADR-004(ECS vs Lambda vs EC2)でも、Lambda不採用の理由としてRDS接続数上限とRDS Proxyの必要性まで言及しており、単なる一般論の比較になっていません。

コストの扱いも良い判断です。Auto Scalingの最小・最大タスク数が未確定な段階で、最小構成のみの数字を「コスト見積もり」として書くと実態を過小評価する、と気づき、意図的に記載を見送った上でその理由を明記できています。これは「書けないから書かない」ではなく「書くと誤解を招くから、理由付きで見送る」という判断で、質が高いです。

抜けている点はいずれも構築フェーズで確定すればよい軽微なものです。設計レビューとしては合格とし、構築フェーズ(ECS/ALBリスナー/VPCエンドポイントのTerraform実装)に進んで問題ありません。

## 観点別レビュー

### 設計

- 要件・前提→選定理由→通信経路→セキュリティ設計→可用性設計→コストの各セクションが、内容的に矛盾なく一貫している(例: フロントのDBアクセス禁止という要件・前提が、通信経路・セキュリティ設計双方に正しく反映されている)
- `compute.md`を1ファイルにまとめる判断(B/Cで分けない)を、tfstateの分割基準(blast radius等)とドキュメントの分割基準(内容の重複度)は別軸だと整理した上で行っており、判断基準の混同がない
- 今回の検討過程で見つかった既存レイヤー(`database.md`・`security-group.md`)への影響を、場当たり的に直すのではなく、影響範囲を`infra/`全体まで検索して洗い出し、`terraform validate`で構文面も確認してから修正している。設計ドキュメントの修正が実装まで正しく波及するかを都度検証するプロセスが徹底されている

### セキュリティ

- SG(API限定のRDSアクセス)・DB GRANT(B/C×2ユーザー)・IAM(Secrets Managerの取得範囲をB/Cで分離)・Cognito認証(ALBレベル)の4層が、それぞれ独立した脅威に対応しており重複がない
- コンテナ分離の効果について「同じ言語・似たDockerfileなら同じ手口で侵害される可能性がある」という限界を自ら明記しており、対策の効果を過大に見積もっていない
- **抜け(構築フェーズで確定)**: DBユーザー作成用RunTaskが使うIAMロールの権限範囲が未確定。通常のAPIタスクロール(B/Cそれぞれ自分の秘密情報のみ取得可能)とは異なり、RunTaskはマスターユーザーのシークレットにアクセスする必要があるため、api-b/api-cの通常のタスクロールをそのまま使い回すと、常時稼働しているAPIコンテナがマスター認証情報に到達できる状態になり、`compute.md`が定めた最小権限の原則(28行目)に反する。RunTask専用の別ロールを用意し、マスターシークレットへのアクセスをそのロールのみに絞る設計が必要

### 可用性

- `desired_count`を2以上にする判断が、Auto Scaling(次回セッション)を待たずに今回のセッションで確保できる最低限の冗長性として適切に切り分けられている
- 新規追加するSecrets Manager用VPCエンドポイントを、既存の`ecr.api`/`ecr.dkr`/`logs`と同じ「各AZに1つ」のパターンに揃えており、新しいSPOFを生まない判断ができている

### 運用性

- ECSコストの記載見送り、Fargateタスクサイズの決定理由、RunTaskの経路など、セッション中に判断した内容とその理由が`compute.md`本体に過不足なく残っており、後から読んでも意図を追える状態になっている
- 既存レイヤーへの修正(`database.md`・`security-group.md`)を、レビュー記録側にも追記できており(2026-08-20付)、「完了」判定済みの成果物が後から変わった経緯が追跡可能になっている

### 保守性

- フロント/APIのFargateタスクサイズを、現時点でのデータ不足を理由に無理に差別化せず、同一サイズに揃えた判断は、根拠のない先回りの最適化を避けられている
- ALBのパスパターン(`/b/front/*`・`/b/api/*`等)が、AWSの実際のリスナールール構文(グループ化構文非対応)を踏まえた具体的な記法に修正されており、実装時に迷わない状態になっている

### コスト

- Secrets Manager用VPCエンドポイントのコストが、既存のAZごとの単価($0.014/h)を使って正しく計算されている($20.44/月)
- ECSのコストを「最小タスク数のみの見積もりは実態を過小評価するため、Auto Scaling設計時に記載する」として意図的に見送った判断は、見積もりの網羅性よりも正確性を優先する、実務でも通用する判断
- **抜け(構築フェーズで確定、優先度低)**: ECSタスクを実際に`apply`して動作確認する際、desired_count=2・256/512MB構成での概算コストが分からないままだと、確認作業中にどの程度課金されるか把握しづらい。コスト見積もりとして「記載」はしないとしても、apply前に概算だけ暗算しておくとコストガードレールの運用上安心

### パフォーマンス

- CSR採用によるLCP悪化を明確に認識した上で、その代償(フロント→API間の同期結合によるノイジーネイバー化)と比較して判断しており、パフォーマンスとアーキテクチャ原則の両方を天秤にかけられている
- Fargateタスクサイズ(256/512MB)は、現状トラフィックが実質ゼロという前提と整合しており、過剰プロビジョニングになっていない

### Terraform化した場合の改善点

- DBの認証情報をタスク定義に渡す際は、環境変数に平文で書かず、`secrets`(`valueFrom`でSecrets Manager ARNを指定)を使う実装にする(ADR-002のstate管理方針とも一貫する)
- RunTask用のタスク定義・IAMロールは、api-b/api-cの通常のサービス用タスク定義とは別リソースとして分離する(上記セキュリティの指摘に対応)
- ALBリスナールールは、`/b/api/*`のような優先度の高い(より具体的な)パターンを、`/b/*`のような広いパターンより先に評価されるよう、`priority`の設定に注意する

### AWS Well-Architected Framework 6本柱

- 運用上の優秀性: 判断理由・持ち越し事項がすべて文章化されており、追跡可能性が高い
- セキュリティ: 多層防御が一貫した最小権限の原則で設計されている。RunTaskのIAMロール分離のみ未確定
- 信頼性: `desired_count`≥2・VPCエンドポイントのAZ分散により、Auto Scaling前でも基本的な冗長性が確保されている
- パフォーマンス効率: 現状トラフィックに対して過不足のないサイジング。CSR採用によるトレードオフも自覚的
- コスト最適化: 実態を反映しない数字を書かないという判断も含め、見積もりの誠実性が高い
- 持続可能性: 直接の言及はないが、最小サイジング+後からの変更容易性の組み合わせにより過剰プロビジョニングを避けられている

### 実務ならどう設計するか

- 今回のセッションの一番の価値は、「フロントのDBアクセス」という一見小さな論点から、既存2レイヤーの手戻りを発生させつつも、場当たり的に済ませず影響範囲を全部洗い出して直し切った進め方そのもの。実務のレビューでも、後から見つかった前提の誤りにどう向き合うかで設計者の質が測られることが多く、今回のプロセスはそのまま通用する
- 実務であれば、RunTask用IAMロールの分離は、レビューで最初に指摘される類の項目。マスター権限を持つロールの棚卸しは、侵害時の被害範囲に直結するため優先度が高い

## 理解できていること

## 理解できていること

- Execution RoleとTask Roleの役割の違い、および`secrets`によるSecrets Manager値の注入がExecution Role側の仕事であること
- `family`とリビジョンの関係、CI/CDが新しいリビジョンを登録しサービスを更新することでTerraformの`lifecycle.ignore_changes`と役割分担する仕組み
- `iam:PassRole`が必要になる正確なタイミング(ロールを他のリソースに割り当てようとする瞬間)
- IAMの信頼ポリシー(誰が引き受けられるか)と権限ポリシー(何ができるか)の違い
- Cognitoの User Pool・Client・Domainそれぞれの役割、OAuth2の「Client」という用語の意味
