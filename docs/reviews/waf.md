## 総評

壁打ちを通じて、最終的な設計内容は正確で一貫性が取れており、設計レビューとしては合格とし、構築フェーズ(Terraform実装)に進んで問題ありません。

今回最も評価したいのは、**「CloudFrontが唯一の入口」という、これまでこのプロジェクトが前提にしてきた理解に対し、Cognito Hosted UIという例外(認証フローの一部がCloudFrontを経由せず直接AWS管理ドメインに到達する)を、自分自身が書いた`cognito.md`の記述を手がかりに正しく認識し直せた**ことです。さらに、この「正規の導線」と「攻撃者が実際にできること」を区別する視点が身についていることを、直後のDDoS対策の議論(Cognito Hosted UIのURL直叩き)で自力で応用できていた点も良い進歩です。

一方で、Web ACL・アカウント乗っ取り対策(ATP)といったAWS WAF固有の機能・料金体系については前提知識が無い状態からのスタートで、マネージドルールグループの一覧を提示されてからATPを選び出す、公式ページでの料金体系の誤りを指摘されて修正する、といった場面がありました。これ自体は初めて触る領域として自然なことですが、コスト計算では前回(`cloudfront-route53-acm-s3`)の実装レビューでも指摘した「単位の取り扱いのミス」(リクエスト数の桁ズレ)が今回も発生しており、この点は明確な傾向として意識してほしいところです。

## 観点別レビュー

### 設計

- Web ACLを3つ(CloudFront用/us-east-1・Cognito User Pool B用/ap-northeast-1・Cognito User Pool C用/ap-northeast-1)に分ける構成は、「WAFは実際にリクエストを受け止める入口ごとに必要」という原則を、CloudFrontとCognito Hosted UIという2種類の異なる入口に対して正しく適用できている
- B/C非対称の設計(B: DDoS対策のみ、C: DDoS対策+ATP)は、`cognito.md`で既に確立していた「B側はMFA必須・C側は任意」という乗っ取りリスクの非対称性の考え方を、そのままWAFの構成にも一貫して延長できている

### セキュリティ

- SQLi/XSS対策について、「アプリケーション層(Django ORM・Next.jsのエスケープ)で既にある程度対策されているが、入口段階で不正なリクエストそのものを弾く」という多層防御の位置づけを自分の言葉で説明できた
- クレデンシャルスタッフィングへの対策検討で、「IPアドレスは変わりうる」「単純なレート制限は繁忙期の正規ユーザーを誤って弾きかねない」という、実務でも指摘される2つの弱点を自力で言語化できたのは良い着眼点。その上でAWS WAF Fraud Control ATP(アカウント乗っ取り防止)という、ログイン試行のパターン自体を評価する専用の仕組みにたどり着けた
- Blockモードを最初から採用する判断(Countモードで様子見せず、被害リスクを優先する)と、それに伴う誤検知時の切り分け手段としてログ取得を追加した判断は、一連の流れとして筋が通っている

### 可用性

- 当初「可用性設計として特に準備できることはない」としていたが、DDoS対応マネージドルールグループの採用自体が可用性設計の内容にあたる、という指摘を受けてすぐに修正できた
- DDoS対策の要否をCognito側のWeb ACLにも広げる判断(Cognito Hosted UIのURLは一度リダイレクトを経験すれば誰でも入手できる公開情報であり、正規の導線を経由せず直接大量リクエストを送りつけられる、という認識)は、このセッションで最も評価できる洞察の一つ

### 運用性

- ログ取得なし+Blockモードという組み合わせのリスク(正規リクエストが誤検知で弾かれた際に、アプリのバグかWAFによるブロックかを区別する手段が無くなる)を指摘した際、一度「ログは不要」とした判断をすぐに見直し、ログ取得を追加できた

### 保守性

- Cognito用Web ACL(REGIONAL)のtfstate配置を、「どのAWSリソースに紐づくか」ではなく「変更頻度・責務がWAFに近い」という、既存のtfstate分割基準(変更頻度・ライフサイクルの独立性・blast radius・権限境界)に立ち返って判断できた。これはALBを「論理的に1つ」と扱った過去の判断(役割・責務で線引きする考え方)とも一貫している

### コスト

- 初回の試算では、ATPを他の標準マネージドルールグループと同じ$1/月のルールとして扱い、しかもその1ルールとしてすら合計数(5個)に含め忘れており、結果としてATPのコストがまるごと計上されていなかった。公式ページ(https://aws.amazon.com/waf/pricing/)で、ATPが$10/月の固定費+従量課金という別建ての料金体系であることを確認した上で指摘し、修正できた
- 修正後もリクエスト数の計算式(`$0.6 * 1000 / 100000`)に桁のズレ(100万を100,000と誤って計算)が残っている。合計額への影響は無視できる範囲だが、`cloudfront-route53-acm-s3`の実装レビューでも同種の単位ミス(1,000リクエスト単価の掛け違い)を指摘しており、**単位・桁の取り扱いは複数セッションにまたがる継続的な弱点**として意識してほしい
- 最終的な合計(約$30/月、Web ACL 3個+ルール5個+ATP固定費+リクエスト従量課金)は、実運用(destroy運用でほぼ無課金)とは別に、常時稼働を想定した理論値として記載する方針を維持できている([[cost-section-convention]]参照)

### パフォーマンス

- WAFの評価はCloudFrontのエッジ・Cognitoのリクエスト処理に組み込まれる形で行われ、追加のネットワークホップを挟まないため、特筆すべき懸念はない

### Terraform化した場合の改善点

- CloudFront用Web ACL(us-east-1、スコープ`CLOUDFRONT`)は、既存の`route53-acm`レイヤーで導入済みのus-east-1 provider aliasをそのまま再利用できる
- Cognito User PoolへのWeb ACL関連付けは`aws_wafv2_web_acl_association`(`resource_arn`にUser Pool ARNを指定)で行う。ALBへの関連付けと同じリソースタイプなので、実装パターン自体は流用できる
- CI/CD(WAFレイヤー用OIDCロール)のIAMポリシーに、`wafv2:*`関連の権限(Web ACL作成・マネージドルールグループの追加・`AssociateWebACL`)を追加する必要がある。これも「stateアクセスとIAM権限は別軸で絞る」という既存の方針([[cicd-access-design-deferred]]参照)に沿って対応する

### AWS Well-Architected Framework 6本柱

- 運用上の優秀性: 誤検知時の切り分け手段(ログ)を運用開始前に組み込めている
- セキュリティ: 多層防御(アプリ層+WAF)、脅威ごとの適材適所のルールグループ選定(CRS/既知の不正な入力/ATP/DDoS対応)、B/Cのリスク非対称性を反映した構成、いずれも妥当
- 信頼性: DDoS対応マネージドルールグループを、CloudFrontだけでなくCognito側の独立した入口にも適用する判断ができている
- パフォーマンス効率: 特筆事項なし(エッジでの評価に統合される)
- コスト最適化: 固定費が支配的な料金体系(特にATP)を理解した上で、B側は不要と判断してコストを抑えている。一方で計算の正確性には改善の余地が残る
- 持続可能性: 特筆事項なし

### 実務ならどう設計するか

- 「正規のユーザー導線」と「攻撃者が実際に取りうる経路」を区別して考える視点は、WAF・SGに限らずセキュリティ設計全般で重要な習慣であり、今回のセッションで実践できていた
- コスト試算における単位・桁の取り扱いミスは、実務でも見積もりの信頼性を損なう典型的な失敗パターン。計算後に「桁数がおかしくないか」を一度検算する習慣を意識すると良い

## 理解できていること

- 多層防御の考え方(アプリ層で対策済みでも、入口段階で弾く価値がある理由)
- Cognito Hosted UIがCloudFrontを経由しない独立した入口であること、およびそのURLが正規の導線を経由しなくても直接アクセス可能な公開情報であること
- クレデンシャルスタッフィング対策として、IPベース・単純レートベースの限界と、ATP(ログイン試行パターン自体を評価する仕組み)の位置づけの違い
- tfstate分割の基準が「リソースの種類」ではなく「変更頻度・責務・blast radius・権限境界」であること

## 曖昧なこと

- ATPの実装レベルの挙動(Cognito User Poolに直接アソシエートした場合、ログインフォームのリクエスト検査設定がどこまで自動化されるか)は、構築フェーズで実機確認が必要

## 理解できていないこと

- 特になし。会話の中で生じた疑問点(ATPの料金体系、Cognito Hosted UIの経路、コスト計算の誤り)は、いずれもその場で解消できている
