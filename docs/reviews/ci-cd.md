## 総評

デプロイ方式の検討(ローリング vs Blue/Green)は、コスト増・移行の容易さ・現時点で問題になるユースケースが想像できないことを根拠に「今は不要、後から低コストで変更できる」という可逆性ベースの判断ができており、`database.md`と同じ質の思考ができています。

一方で、`.claude/DESIGN_NOTES.md`側で既に決着している内容の一部が`ci-cd.md`に反映されておらず、テンプレートの必須セクション(可用性設計・コストの見積もり)も空欄のままです。特にOIDC用IAM Roleの権限粒度は、これまでB/C分離で一貫してきた「侵害時の被害限定」という設計原則をCI/CDの認証情報にも適用するかどうかという設計判断そのものなので、書き忘れではなく一度考えてから埋めてください。設計レビューとしてはここで差し戻し、Terraform実装には進まないでください。

## 観点別レビュー

### 設計

- 良い点: 「選定理由」でのデプロイ方式の検討は、決め打ちではなく可逆性(後から容易に移行できるか)を軸にしており、判断の質が高い
- 抜け: `.claude/DESIGN_NOTES.md`の「CI/CD方針確定・DBユーザー作成の置き場所」(2026-08-17)で決着した内容 — `api-b`/`api-c`のOIDC権限を使った一度限りのECS RunTaskでDBユーザー作成SQLを実行する、`workflow_dispatch`の別ジョブとして用意する — が`ci-cd.md`に一切出てこない。今回のスコープがコンピュート非依存部分のみだとしても、決定済みの設計判断なら「この部分はコンピュート層構築時に追記する」のような一文を残した方が、後から読んだときに「決めていない」のか「対象外」なのか判別できる

### セキュリティ

- 良い点: OIDC連携で長期認証情報を排除する判断は明確
- 未決定(要検討): OIDC用IAM Roleの権限粒度が書かれていない。4つのワークフロー(front-b/front-c/api-b/api-c)に対してIAM Roleを1つ共有するのか、B/C単位(または4つ)に分けるのか。B側ワークフローの認証情報が万一漏洩した場合に、C側のECRリポジトリにもpushできてよいか、これまでB2B/B2C分離で採用してきた「侵害時の被害限定」の原則がCI/CDの認証情報にも当てはまるかどうか、一度考えてみてください
- 未検討: ECRのイメージスキャン(`scanOnPush`)への言及がない。イミュータブルタグでロールバックできる設計にはなっているが、脆弱性のあるイメージをpushした時点で検知する仕組みとは別問題

### 可用性

- セクション自体が空欄。CI/CDパイプラインにおける可用性が何を指すか(GitHub Actions自体の障害時の代替手段の要否、ECRを単一リージョン運用のままで問題ないか等)を一度検討し、「対応不要」という判断であっても、他のドキュメント同様に理由込みで明記してください

### 運用性

- 良い点: pathsフィルターで無駄なビルドを避ける判断理由は明確
- 抜け: トリガー条件(いつ実行するか)が書かれていない。mainブランチへのpush時のみか、PR時にはビルド・push無しでlint/testだけ走らせるのか
- 抜け: ECRのライフサイクルポリシー(古いイメージタグをいつまで保持するか)。イミュータブルタグ運用は、放置すると際限なくイメージが積み上がる

### 保守性

- 「Terraformとの境界」でタスク定義の型とイメージタグ更新の役割分担は明確
- 未決定: ECRリポジトリ・OIDC用IAM Role・IAM Identity ProviderがTerraformのどのstateレイヤーに属するか書かれていない。既存のstate6分割(ネットワーク+SG+ALB / CloudFront・Route53・ACM・S3 / WAF / コンピュートB / コンピュートC / データベース)のどこにも「CI/CD基盤」に該当するレイヤーがない

### コスト

- セクション自体が空欄。GitHub Actionsの実行時間課金(privateリポジトリの場合)、ECRのストレージ課金(4リポジトリ×イミュータブルタグを貯め続けた場合)を、他のドキュメント同様に試算してください

### パフォーマンス

- pathsフィルターによるビルド時間短縮は運用性と重複するため、こちらでの追記は不要

### Terraform化した場合の改善点

- OIDC用のIAM Identity Provider・IAM Role・ECRリポジトリは、他レイヤーとの依存関係(誰が何にassumeできるか)が明確になるようTerraformでコード化すべき。backend用S3バケットのような「鶏と卵」問題の対象にすべきかどうかも合わせて検討する

- 運用上の優秀性: pathsフィルターによる無駄削減は良い判断。トリガー条件・テスト実行の有無が未確定
