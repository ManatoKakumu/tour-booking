## 総評

良い出来です。トリガー方式の検討で、当初案(メトリクス検知)の弱点(事後対処になる、原因の切り分けが困難)を自ら見抜けた点、「EventBridgeでメール受信を検知したい」というアイデアが技術的に成立しない理由を理解した上で方針転換できた点は評価できます。最終的に「手動実行のみ」という結論にたどり着く過程で、一度「保険としての定期cron併用」に傾きかけましたが、コストがほぼ$0という前提のもとでは「保険cronだけで十分では」という矛盾に自分で気づき、最終的に「まだ起きていないリスクのために先回りで保険を作らない」という、このプロジェクトで一貫してきた判断パターン(ElastiCache不採用・RDS/Aurora据え置き)に立ち返れたのは良い到達点です。

tfstateの配置(ADR-002)では、一度「変更頻度が低いから既存のstateに同居させる」という、このドキュメント自身の分割方針(59〜61行目、無駄なスキャンの回避・blast radiusの限定)と矛盾する結論を書いてしまいましたが、指摘後に`ECRライフサイクル`の前例と整合する形(独立state)へ修正できています。

セキュリティ設計では、`ec2:DescribeManagedPrefixLists`のような「Describe系アクションの多くはリソースレベル権限に対応していない」というAWS IAMの技術的制約を、実装前の設計段階で踏まえられた点が良い判断です。可用性設計でも、同時実行数を1に絞る理由が、当初「クオータ圧迫の回避」という的外れな理由から、指摘を受けて「プレフィックスリスト更新の競合防止」という正しい理由に修正できています。

コスト見積もりは、実行回数の想定(月1回程度)と計算式に使う数値(100回、`ecr-lifecycle`からの残存)が食い違ったまま提示されかけたり、実行時間を掛け忘れて計算結果が1桁誤っていたりと、細かい修正が複数回必要でしたが、いずれも指摘後正しく直せています。ただし49行目の単位表記(「40万GB/月」)は最後まで直っていないので、次のアクションに残します。

設計レビューとしては合格とし、構築フェーズ(Terraform実装、Lambda関数の実装)に進んで問題ありません。

## 観点別レビュー

### 設計

- 「SGルール自体は1つのまま変えず、プレフィックスリストのエントリだけを更新する」という処理の切り分けが、通信経路に正確に反映されている
- トリガー方式(手動実行)の検討過程で、代替案(メトリクス検知・cron定期実行・SES経由のメール検知)をそれぞれ比較し、却下理由を明確にできている(ADR-005)
- Lambda実行環境をVPC外に置く判断が、要件(VPC内部リソースとの通信不要)とコールドスタート回避の両面から適切に導かれている

### セキュリティ

- IAM権限を3アクション(`ModifyManagedPrefixList`・`GetManagedPrefixListEntries`・`DescribeManagedPrefixLists`)に絞り込み、かつリソースレベル許可が使えないアクション(`Describe`系)は`Resource: "*"`にせざるを得ない、というAWS側の制約を正しく踏まえた設計になっている
- SGへの0.0.0.0/0許可を避けたい、という要件・前提の動機付け(侵害時の被害範囲)が明確に書かれている

### 可用性

- 同時実行数を1に絞る理由が、当初の「クオータ圧迫の回避」という誤った理由から、指摘を受けて「プレフィックスリスト更新(楽観的ロック)の競合防止」という正しい理由に修正できている
- 失敗時通知を設けない判断が、手動実行という前提(実行者がその場で結果を確認できる)と整合している。`ecr-lifecycle`(EventBridgeによる自動実行、失敗を検知する主体が別途必要)とは前提が異なることを踏まえた、意図的な判断になっている

### 運用性

- Stripeが変更7日前に予告メールを出す、という外部サービスの実際の運用ポリシーを自分で調査した上で設計に反映できている(参照: docs.stripe.com/ips)
- **軽微な指摘**: 「手動実行のみ」という運用は、実行者が通知メールを見落とすリスクを構造的に抱えている。この残存リスクを許容する判断自体はADR-005でなされているが、「なぜ許容できるか」の記載はやや薄く、最終的に「特にない」という記述が残っている

### 保守性

- ADR(005・002)への参照リンクを設計文書側から明記しており、後から経緯をたどりやすい構造になっている
- 「Lambda選定理由」と「手動実行の選定理由」を見出しレベルで分離できており、2つの異なる決定を混同していない

### コスト

- 計算過程で、実行回数の想定(月1回程度)と計算式の数値(100回、`ecr-lifecycle`からの残存)の不一致、計算式の掛け忘れ(実行時間分)、単位の誤記(GB/GB秒)と、複数の小さなミスが段階的に見つかったが、いずれも指摘後に修正できている
- 結論($0)自体は最初から変わっていない
- **軽微な指摘**: 49行目にまだ「40万GB/月」という表記が残っている(45行目は修正済みだが、こちらは見落とされている)。次のアクションに残す

### パフォーマンス

- 特筆事項なし(低頻度・軽量処理のため、パフォーマンス上の懸念は小さい)

### Terraform化した場合の改善点

- `infra/stripe-ip-sync/`を新規の独立ディレクトリ・tfstateとして構築する(`infra/ecr-lifecycle/`のディレクトリ構造・`lambda/handler.py`+`archive_file`のパターンを踏襲できる)
- IAMポリシーは、`ModifyManagedPrefixList`・`GetManagedPrefixListEntries`をプレフィックスリストのARNに絞ったステートメントと、`DescribeManagedPrefixLists`用に`Resource: "*"`のステートメントを分けて2つ用意する
- Lambdaに`reserved_concurrent_executions = 1`を設定する

### AWS Well-Architected Framework 6本柱

- 運用上の優秀性: Stripe側の公式な通知手段(7日前予告メール)を運用に組み込めている
- セキュリティ: 最小権限の原則を、AWS側の技術的制約(Describe系アクションの制限)まで踏まえた上で実現できている
- 信頼性: 手動実行に伴う残存リスク(見落とし)を認識した上で許容しており、隠れたリスクにはなっていない
- パフォーマンス効率: 低頻度・軽量処理に対して過不足のない構成
- コスト最適化: 全コンポーネントが無料枠内に収まる計算ができている
- 持続可能性: 特筆事項なし

### 実務ならどう設計するか

- 「まだ起きていないリスクのために先回りで保険を作らない」という、このプロジェクトで一貫している判断パターン(ElastiCache不採用・RDS/Aurora据え置きと同じ)を、トリガー方式の選定でも一貫して適用できた
- 一方で、外部サービス(Stripe)の運用ポリシー(7日前予告)に前提を置く設計は、そのポリシー自体が変わった場合に前提が崩れるリスクがある。実務では、こうした外部依存の前提を定期的に再確認する仕組み(ドキュメントの棚卸しなど)もセットで検討されることが多い

## 理解できていること

- マネージドプレフィックスリストと、それを参照するSGルールの関係(SGルール自体は1つのまま、プレフィックスリストの中身だけが変わる)
- EventBridgeが「発行されたイベントを受け取ってルーティングする」サービスであり、メール受信のような外部イベントを直接検知できないという技術的制約
- `ModifyManagedPrefixList`が楽観的ロック(バージョン管理)で更新されるため、同時実行時に競合しうるという仕組み
- EC2のDescribe系アクションの多くがリソースレベル権限に対応していないというIAMの制約

## 曖昧なこと

- 「保険としての定期cron」を最終的に不採用としたが、Stripeの通知ポリシー自体が変わった場合(例: 予告なしでの変更に切り替わる等)にどう気づくか、という運用上の見直しタイミングは明記されていない
