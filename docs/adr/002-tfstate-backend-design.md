# ADR-002: Terraform stateのバックエンド設計

## ロック機構

### なぜロック機構を設けるのか
- ロック機構を設けないことは、ローカルで各自ステートを管理する際に直面する問題と同じ問題に直面する。それは以下のような問題である
  - AさんとBさんがそれぞれステートを独自のローカル環境で管理する運用だとする
  - AさんがEC2を追加、BさんはAさんの変更内容を反映したステートを自身のステートに取り込まずに別でEC2を追加したとする
  - AWS上、tfファイル上ではEC2は2台だが、ステートはBさんのステートで上書きされ、EC2は1台存在することになる
  - この状態でEC2をさらに追加すると、tfファイルでは3台だがステートでは1台なので、差分で2台を追加しようとし、AWS上では2+2=4台起動し、実態とtfファイルに乖離が起き、tfファイルがドキュメントとしての信ぴょう性を持たなくなる
  - こうなると、tfファイルを見ただけでは気づきにくい隠れリソースの料金発生、隠れNACLの適用によりリソースへの通信ができない、などのトラブルに気づきにくい可能性が出る
  - これはローカルで各自ステートを管理している場合の問題であったが、ステートを1箇所で管理していても、ロック機構がなければ結局同じ問題が発生しうるため、1箇所管理+ロック機構を設定する必要がある

### 今回のロック機構
- S3 + DynamoDBによる構成もあるが、S3ネイティブロックを採用する
- ネイティブロックはDynamoDBが不要でロック機構を採用でき、リソースを必要最小限で要件を満たすことができるため、今回はネイティブロックとする

## 鶏と卵問題

### なぜこの問題を考慮する必要があるのか
- S3バケット自体をTerraformで管理しようとすると、そのTerraformが使うbackend(state書き込み先)として、まさにこれから作ろうとしているS3バケットを指定することになる。しかしterraform initの時点でbackend先のバケットが存在していないとTerraform自体が動かせないため、「バケットを作るには、先にバケットが存在している必要がある」という堂々巡りが生じる。
- 解決方法として、下記が考えられる
  - ステート管理用のS3だけは手動で作成する
  - ステート管理用のS3のみはtfファイルで記載+ステートをローカル管理
  - ステート管理用のS3のみはtfファイルで記載+ステートをgit管理

### 今回の構成
- ステート管理のS3バケットは手動で構築する。以下より、今回はこの構成にした
  - git管理は、ステートに機密情報が平文でのる可能性があり、情報漏洩のリスクがあるため却下。また、ロック機構がない、という問題にも直面する
  - ローカルでステート管理も、ステートの管理がローカルとS3にあり、混乱のもとになる。また、ステートはローカル環境に依存するため、仮にファイルが破損した場合、ステートなし→未実行である、と誤認され、バケットの作成が行われる可能性がある（とはいえ、S3バケットなので名前ユニーク制約に引っかかって気づきやすい状況ではあると思われる）

## バケット設定

### 暗号化
- ON(SSE-S3)
- ステートには機密情報（DBへの接続情報など）が含まれるので、だれでも見れる状態を作ってはいけない
- SSE-KMSも選択肢として考えられるが、これは以下のような用途で選択されるケースだと判断したが、今回のステート管理においてはそのようなケースは考えられないと判断し、SSE-S3を選択した
  - 従業員データを格納したS3バケットがあるとする
  - 社員であれば全員アクセスできる
  - このバケットの中に給料情報という、給与管理系の人物だけがアクセスできるべき情報が入っており、社員全員のアクセスを許可したいが、一部のファイルだけはアクセスできる人を絞りたいユースケースが存在する
  - このような場合に、IAMユーザ+グループなどにより、KMSによって、特定のフォルダへの暗号化キーを用いた複合が可能となるポリシー制限を課すことで、要件を達成できる

### バージョニング
- ON
- ステートが消える、変更したが何らかの問題が発生した、などの場合でも、うまく動いていた最新のバージョンに戻すことで、インフラへの更新作業にかかる時間を短縮することができる

### パブリックアクセス
- ブロック
- ステートには機密情報（DBへの接続情報など）が含まれるので、だれでも見れる状態を作ってはいけない

## state分割

### なぜ分割するのか
- 変更頻度の高いものと低いものが同じtfファイルにあると、頻度の低いものも高頻度でplan/apply時などにスキャンされ、無駄になる+処理時間が長くなるため、適切な粒度で分割するのが望ましい
- 1つのファイルにすべてを記載すると、例えば問題発生時にネットワーク関連と思われても探すのが困難になるので、大きな役割ごとにファイル分割する方が運用コストを低く保てる
- 仮に問題が発生した際に、

- 以上より、下記方針にてファイル分割する
  - 更新頻度の近いもの
  - 役割が近いもの（曖昧な表現になってしまっているが、NW・DB・コンピュート、程度の粒度）

### 分割方針
- NW / SG / ALB
  - 他のリソースに比べて変更頻度が少なく、役割としては全ての土台となるもの
- CloudFront / Route53 / ACM / S3(静的ページ)
  - コンピュート層が全滅しても生き残るべき層
  - 大規模な障害が起きても、会社概要ページは配信し、電話によるオペレーション継続をさせるべき、という考えに基づく分離
- WAF
  - セキュリティルールの変更など、CloudFrontなどと比べて変更頻度が高くなると想定されるため分離
- B側コンピュート(ECS / Elastic cache)
  - コンピュート層+B/Cで分ける、という方針に一貫性を持たせる
- C側コンピュート(ECS / Elastic cache)
  - コンピュート層+B/Cで分ける、という方針に一貫性を持たせる
- RDS
  - DBという役割で分離
