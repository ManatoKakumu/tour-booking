# ADR-001: IaC・Terraformの採用

## コンテキスト
- インフラ構築において、手動作業や複数のIaCなど、候補が複数ある

## 選択肢
- 手動
- terraform
- その他IaC(CloudFormation、Ansibleなど)

## 決定
- terraform

## 理由
- 今回は本番（想定）アカウントしかないが、本番環境へ直接追加や修正を行うのはリスクが高いため、テストアカウントを用いてその環境で動作確認してから本番環境に適用するのが望ましい。この前提で、手動かIaCかを下記の観点から判断した
  - 手動で作業する場合のデメリット：設定ミスが起きやすく、時間もかかる。同じ構成を別の環境に再現するには、同じ手順をもう一度手で繰り返す必要がある。ドキュメントがあってもそれが実態とかけ離れていき信用ならないものになる可能性がある
  - IaCで作業する場合のメリット：同じコードから同じ構成を別の環境にも再現できる。また、バージョン管理が可能になるので、なぜどのような理由でリソースの追加や修正が行われたかが把握しやすい。不具合が発生した場合は古いバージョンに戻すことが可能。レビューされてから適用する運用にすることが可能
  - 以上より、IaCで管理することとした
- IaCはいくつかあるが、terraformを選んだ理由として、以下を挙げる
  - Ansibleのような手続き型ではなく宣言型言語であり、明確で読みやすい
  - CloudFormationはAWS専用だが、terraformはマルチクラウドや、オンプレ+クラウドなどの環境でも一元管理が可能で、将来的な拡張に強い。今回の構成で管理しているのは実質AWSのみだが、例えば現在は手動で設定しているGitHub側の設定(Environments・Repository Variablesなど)も、同じツール・同じ書き方で管理対象に加えられる
  - planやapply手前など、インフラへの変更前に適用予定の差分が確認できる。ただし、差分をよく確認せずに適用すると、意図しないリソースの再構築などの事故につながる点は認識しておく(影響範囲を抑えるためのstate分割は[ADR-002](002-tfstate-backend-design.md)参照)

## 結果
- 今回は個人開発であること、および金銭的コストを考慮し、作業のたびにリソースを構築しては削除する、を繰り返した。毎回同じ構成をコマンドだけで再現できたため、手動作業よりもterraformで管理したのは作業手順が楽になり、良かったと考える
- 一方で、`network-sg-alb` と `cloudfront-s3` のステートが循環参照になり、初回構築のたびに該当箇所をコメントアウトしてから反映する、という手順が必要になった点はやや面倒であった(詳細は[ADR-002](002-tfstate-backend-design.md)参照)
