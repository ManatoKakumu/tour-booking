# ADR-001: IaC・Terraformの採用

## コンテキスト
- インフラ構築において、手動作業や複数のIaCなど、候補が複数ある

## 選択肢
- 手動
- terraform
- その他IaC(CloudFormation、Ansibleなど)

## 決定
- terraform

## 理由
- 今回は本番（想定）アカウントしかないが、本番環境に追加や修正を行うのが怖いので、テストアカウントを用いてその環境で動作確認してから本番環境に適用するのが望ましい。その場合、手動で作業をすると、設定ミスや時間がかかる、ドキュメントがあってもそれが実態とかけ離れていき信用ならないものになる可能性がある。また、IaCであれば、バージョン管理が可能になるので、なぜどのような理由でリソースの追加や修正が行われたか、古いバージョンに戻す、レビューされてから適用する運用にする、などが可能となる。そのため、手動作業ではなくIaCを採用したい。
- IaCはいくつかあるが、terraformを選んだ理由として、以下を上げる。
  - 手続き型ではなく宣言型言語であり、明確で読みやすい。
  - マルチクラウドサービスや、オンプレ+クラウドなどの環境でも一元管理が可能で、将来的な拡張に強い。
  - planやapply手前など、インフラへの変更前に適用予定の差分が確認できる。ただし、これは後の002-arcでも記載するが、注意しないと事故につながることでもある点は認識しておく。
