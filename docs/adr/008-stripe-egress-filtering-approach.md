# ADR-008: Stripe向けアウトバウンド通信のフィルタリング方式選定

## コンテキスト
- 現状、ECS APIからのアウトバウンド通信をStripeのみに絞る手段として、Lambdaの実行でプレフィックスリストの中身(IPエントリ)を更新し、SGのルールがそのプレフィックスリストを参照することで、通信先IPアドレスを絞る方針にて実装している
- ただ、この処理の実装中に、SGのデフォルト上限に達したため、上限を上げる申請リクエストをした。このときに、そもそも上限を上げる申請リクエストをする状況になっていることを改めて考慮しなおしたほうがいいと考えた
- 他にも何か手段がないか検討した際の記録をここに記載する

## 選択肢
- 現状維持（SG+マネージドプレフィックスリストによるIPアドレスベースの制御）
- Network Firewallの導入
- Proxyコンテナを経由

## 決定
- 現状維持（SG+マネージドプレフィックスリストによるIPアドレスベースの制御）

## 理由
- Network Firewallの導入
  - Stripeの公式ドキュメントにも、現状のようなIPアドレスでの制御ではなく、ドメインによる制御が推奨、と記載されている。Network Firewallならば、ECS APIから送信されたSNIを参照し、ドメインを確認して通信の許可拒否を決められる
  - ただ、金銭的コストが高く、見送る
    - エンドポイントだけでも、最初のAZは$0.395/h、2AZ以降は$0.158/hとなる
    - ($0.395 + $0.158) * 24h * 30日 = $398.16
    - この金額は、今回の個人開発では、かなり厳しい。さらには、これ以外にもデータ処理量も加算される
  - なお、仮にNetwork Firewallを導入する場合は、ECS APIサブネットのルートテーブルの0.0.0.0/0の向き先を、NAT GatewayからFirewallエンドポイントに向ける必要がある
- Proxyコンテナ
  - Network Firewallは金銭的コストで懸念があった
  - そこで、ECSなどで、ECS APIからの通信を、SNIを参照してStripeのドメインならそのままNAT Gatewayへと通信を流し、そうでなければ拒否する、という処理を自前実装するものである。
  - 金銭的コストの面ではNetwork Firewallよりも優位で、かつIPアドレスによる制御も回避できる。しかし、Stripe宛に通信を絞るという目的自体は、手段(ドメイン名ベース vs IPアドレスベース)は異なるものの、現状のSGでも既に達成できている。そのため、わざわざ自前実装するメリットが薄い。むしろ、開発テスト運用コストが大きくなる
  - なお、仮にProxyコンテナを導入する場合は、ECS APIからNAT Gatewayへの通信の間に、Proxyコンテナを挟むように修正する必要がある
- 現状維持（SG+マネージドプレフィックスリストによるIPアドレスベースの制御）
  - Network Firewallと比較し、金銭的コストの観点で優位
  - Proxyコンテナと比較し、開発テスト運用コストの観点で優位
  - なお、当初懸念していたSGの上限を上げる申請リクエストについてだが、付与できるSGの数や許可ルールが減る、という制約がある。現状の構成ではこの点は問題ない、というのもこの決定の一因である。現状、ECS APIに付与しているSGは1つしかない
  - ただ、仮にStripeのIPアドレスが変更になり、CIDRプレフィックスが上限に達した場合に、再度上限の引き上げ申請を行う必要がある。これが承認されるまでの時間も確定できないので、承認されるまでの間は、一部のIPアドレスが許可されず、Stripe API呼び出しが失敗する可能性があることは認識しておくべき
