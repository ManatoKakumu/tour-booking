# ADR-007: ElastiCacheによるセッション外部化の撤回(ALB+Cognito認証で代替)

## コンテキスト
- 初期段階では、ElastiCacheにセッション情報を保存する想定だった。ECSのオートスケーリングや、ヘルスチェック失敗によるインスタンス置き換えの際に、セッション情報を失わないように、セッション情報の外部化する目的があった
- しかし、設計・実装が進むにつれ、ElastiCacheを外したので、その経緯を記載する

## 選択肢
- ElastiCacheの維持
- ElastiCacheを削除し、ALB+Cognito認証機構を用いる

## 決定
- ElastiCacheの削除

## 理由
- 当初は、書き込み頻度が少なく、読み取り頻度の高いセッション情報をElastiCacheに保存することで、セッション情報の外部化目的があった
- Cognitoの導入によって、ElastiCacheは不要と判断した。ElastiCacheはECSコンテナからアクセスする想定だったが、Cognitoを導入したことにより、認証情報が正しくないとECSコンテナにたどり着かない。つまり、ECSコンテナにたどり着くことは、認証情報が正しいことを意味しており、であればそこからわざわざElastiCacheにセッション情報を参照しに行く必要がないと判断した
- ただし、これはElastiCacheにセッション情報のみ保存する想定だったので成り立つ話であり、かりにセッション情報以外をElastiCacheに保存する想定であれば、ElastiCacheは残したまま、セッション情報の管理だけを廃止する形になっていたはずである。また、将来的にセッション情報以外に保存したいデータが出てこれば、ElastiCacheを導入する可能性はある

## 結果
- front-bは認証が必要だが、未認証でリクエストを送信すると、ECSコンテナではなく、Cognito Hosted UIにリダイレクトされることを確認済
